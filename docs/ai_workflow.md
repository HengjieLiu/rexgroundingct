# AI-Assisted Research Workflow

This page adapts useful workflow patterns from two prior Codex-assisted
research projects into the current ReXGroundingCT repo. The goal is durable
project memory with minimal process overhead: specs before expensive work, small
logs during work, clear closeout after work, and no codebase reorganization.

Reference summaries:

- `../AGENTS/reference_ai_workflows/ai_assisted_research_workflow_summary_doserad2026_2026-07-22_d4053028f76e.md`
- `../AGENTS/reference_ai_workflows/ai_assisted_research_workflow_summary_inrorspline_2026-07-22_2ee1ce9cec77.md`

## Operating Principle

Treat Codex work as project state, not disposable chat. Anything that changes
research direction, launches a long run, moves data, changes challenge
submission behavior, or creates a reusable method should leave a small tracked
artifact that a later session can read.

The lightweight loop is:

```text
request -> execution spec -> smoke/check -> run -> report/sync -> decision/todo update
```

Use this loop for substantial work. Small code fixes and documentation edits do
not need a full spec, but they still need normal checks and a clear handoff.

## Before Work

Start every meaningful session by reading:

1. `AGENTS.md` and the files under `AGENTS/`.
2. `README.md` and the relevant folder READMEs.
3. `docs/current_status.md`.
4. The relevant experiment README, report, config, and spec.
5. `git status --short`, treating existing dirty files as user work.

For challenge decisions, refresh or inspect `challenge_info/README.md` and
`challenge_info/SUMMARY.md`. The top-level Markdown files are summaries of
archived official sources; raw snapshots remain the evidence.

## Experiment Specs

Every substantial experiment or long GPU run should have a
`codex_execution_spec.md` before launch. Use:

```text
docs/templates/codex_execution_spec.md
```

Place experiment-specific specs under:

```text
experiments/<experiment-id>/codex_execution_spec.md
```

Required content is intentionally compact:

- objective and prior evidence;
- in scope and out of scope;
- exact config, data roots, runtime root, and launch commands;
- smoke test or dry-run gate;
- success metrics and stop conditions;
- expected repo-local artifacts after the run.

Do not rename experiment IDs casually. Runtime paths, configs, manifests, and
reports depend on them.

## During Runs

Keep runtime outputs under `/mnt/shengdata1`, not in Git. For long runs, capture
at least:

- command and environment in `run_manifest.json`;
- launch log under the runtime `logs/` directory;
- config snapshot under the runtime `config/` directory;
- checkpoints and predictions under the runtime experiment directory only.

Run the smallest useful gate before expensive work. Current examples are CT
readiness polling, orientation diagnostics, smoke fine-tuning, and quick/global
validation evaluation.

## Closeout

After a run writes new metrics or reports:

```bash
python scripts/rexgroundingct/sync_experiment_index.py
python scripts/rexgroundingct/check_experiment_consistency.py
```

Then update `docs/current_status.md` if the result changes what should happen
next. Use `docs/templates/experiment_closeout.md` when a run needs a concise
human closeout beyond an autogenerated report.

Closeout should answer:

- what ran and from which config;
- whether the smoke or full run passed;
- primary metric and caveats;
- which artifacts are authoritative;
- next decision or stop condition.

## Prompt Archive

Reusable prompts and adapted plans live under:

```text
docs/codex_prompts/
```

Archive polished prompts for repeatable tasks, not raw chat transcripts. Good
candidates include experiment launch planning, submission packaging, challenge
source refresh, and major workflow upgrades.

## Submission Work

Submission packaging has its own challenge-level runbook:

```text
docs/submission.md
```

Before any submission decision, refresh official challenge sources if needed,
verify prediction counts and file names, package a single zip file, and record
the exact model/config/source commit used.

## Canonical Checks

Run the wrapper:

```bash
python scripts/rexgroundingct/check_repo_workflow.py
```

Equivalent manual sequence:

```bash
PYTHONDONTWRITEBYTECODE=1 python -m unittest challenge_info.tests.test_update_challenge_info
python scripts/rexgroundingct/check_experiment_consistency.py
python -m py_compile scripts/rexgroundingct/*.py challenge_info/update_challenge_info.py dataset/download_ct_rate_challenge_subset.py
git diff --check
git diff --cached --check
git ls-files '*__pycache__*' '*.pyc'
```

The final command should print nothing. If it prints tracked cache paths, remove
them from Git and keep relying on `.gitignore` for regenerated local caches.

## What Not To Do

- Do not launch long experiments from vague prompts without a saved spec.
- Do not treat chat history as the only memory of a decision.
- Do not commit CT volumes, masks copied from gated datasets, predictions, logs,
  checkpoints, model weights, caches, tokens, or private runtime artifacts.
- Do not reorganize `scripts/rexgroundingct/` into a package during this
  workflow upgrade. Revisit only after experiment 002 stabilizes.
- Do not use broad `git add .` in this repo.
